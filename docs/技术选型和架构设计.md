# tomato 番茄钟技术选型与架构设计文档

## 1. 项目背景

tomato 是一个运行在 Windows 桌面端的学习番茄钟应用。该软件当前阶段主要实现核心计时功能，强调“简单”和“隐身”两个特点。

“简单”表示软件只保留番茄钟计时所需的核心功能，不引入复杂的任务管理、学习统计、账号系统或云同步功能。“隐身”表示软件在计时开始后默认隐藏运行，不持续占用用户屏幕空间。用户可以通过系统托盘、全局热键或必要的系统提示窗口查看和控制计时状态。

根据需求文档，tomato 的核心页面包括计时设置页面、菜单页面、计时显示页面、计时详情页面和计时完成页面，并包含计时开始提示、专注计时完成提示等弹出窗口。用户初次打开软件后进入计时设置页面，设置专注时间和休息时间后启动计时；启动后软件默认进入后台运行，必要时才显示计时窗口或提示窗口。

## 2. 技术选型

### 2.1 总体技术栈

本项目建议采用以下技术栈：

| 模块         | 技术选择                       | 作用                                                       |
| ------------ | ------------------------------ | ---------------------------------------------------------- |
| 桌面应用框架 | Electron                       | 提供桌面窗口、系统托盘、全局热键、系统通知、应用打包等能力 |
| 前端框架     | React                          | 实现计时设置页、菜单页、计时显示页、详情页、完成页等 UI    |
| 开发语言     | TypeScript                     | 提供类型约束，降低状态和 IPC 调用的维护成本                |
| 构建工具     | Vite                           | 提供快速的前端开发和构建体验                               |
| 样式方案     | Tailwind CSS / CSS Modules     | 快速实现简洁、低干扰的界面风格                             |
| 状态管理     | Zustand / React Context        | 管理渲染进程中的页面状态                                   |
| 本地存储     | JSON 文件，后续可扩展为 SQLite | 保存计时设置，后续保存计时记录                             |
| 打包工具     | electron-builder               | 将应用打包为 Windows 可执行文件                            |

首选技术组合为：

```text
Electron + React + TypeScript + Vite + Tailwind CSS + JSON Storage
```

如果后续加入学习记录、统计分析、任务管理等功能，可以将本地存储从 JSON 文件升级为 SQLite。

### 2.2 选择 Electron 的原因

tomato 的核心需求是桌面端常驻运行、小窗口显示、后台隐藏、系统托盘、全局热键和系统通知。这些能力都属于典型桌面应用能力。

Electron 适合本项目的原因主要包括：

1. **适合桌面窗口管理**

   tomato 需要多个不同形态的窗口，包括设置窗口、菜单窗口、右下角计时显示窗口、详情窗口、完成窗口和提示弹窗。Electron 提供 `BrowserWindow` 用于创建和控制桌面窗口，可以对窗口大小、位置、显示方式、置顶状态等进行控制。

2. **适合实现托盘和后台常驻**

   tomato 启动计时后需要隐藏主窗口，并通过 Windows 的系统托盘入口重新打开菜单或计时窗口。Electron 适合实现这类托盘常驻型应用。

3. **适合实现全局热键**

   需求中提到用户可以通过热键打开菜单页面或计时显示页面。Electron 支持注册全局快捷键，即使应用当前不处于焦点状态，也可以响应用户快捷键操作。

4. **适合复用 Web UI 生态**

   tomato 的页面主要是表单、倒计时、按钮、进度条和弹窗，属于 UI 交互型应用。使用 React、TypeScript 和 Tailwind CSS 可以更高效地实现 Figma Make 生成的界面效果。

5. **具备跨平台扩展能力**

   虽然当前开发平台为 Windows，但 Electron 本身支持使用 Web 技术构建跨平台桌面应用。Electron 官方也说明其基于 Node.js 和 Chromium，可以使用 JavaScript、HTML 和 CSS 构建跨平台桌面应用。

### 2.3 为什么不优先选择 WPF / WinUI

WPF 和 WinUI 都可以实现 tomato，且在 Windows 原生体验上有优势。但本项目当前更适合 Electron，主要原因是：

1. 当前页面设计已经可以通过 Figma Make 生成，使用 Electron 更容易复用 Web 页面结构和样式。
2. tomato 后续可能考虑跨平台，Electron 比 WPF / WinUI 更适合跨平台演进。
3. 项目核心逻辑不依赖 Windows 原生高性能能力，主要是计时、窗口显示、通知和状态控制。
4. 使用 React / TypeScript 可以更方便地实现组件化 UI 和状态管理。

因此，本项目选择 Electron 作为桌面应用框架，而不是 WPF 或 WinUI。

### 2.4 为什么第一版不优先选择 Tauri

Tauri 相比 Electron 更轻量，也支持跨平台。但 Tauri 的系统能力主要依赖 Rust 和插件生态。对于当前阶段而言，项目重点是快速完成核心计时功能，而不是引入 Rust 桌面开发复杂度。

因此，第一版建议使用 Electron。后续如果对包体积、内存占用和启动速度有更高要求，可以再评估 Tauri 作为重构方案。

## 3. 总体架构设计

### 3.1 架构目标

tomato 的架构设计应满足以下目标：

1. **计时逻辑稳定**

   即使窗口隐藏、最小化或重新打开，计时状态仍然应该正确维护。

2. **UI 和业务逻辑分离**

   页面只负责显示和用户操作，不直接承担核心计时逻辑。

3. **窗口管理集中**

   所有窗口的创建、显示、隐藏、关闭、置顶和位置计算都应由统一模块管理。

4. **主进程和渲染进程职责清晰**

   Electron 主进程负责系统级能力，渲染进程负责页面展示。

5. **便于后续扩展**

   后续增加学习记录、统计、任务管理、开机自启等功能时，不需要大幅重构。

### 3.3 分层说明

#### 3.3.1 Main Process 主进程

主进程负责所有系统级能力，包括：

1. 应用生命周期管理
2. 创建和管理多个窗口
3. 系统托盘菜单
4. 全局热键注册
5. 系统通知和提示音
6. 本地设置文件读写
7. 核心计时状态维护
8. IPC 请求处理

主进程是 tomato 的“后台控制中心”。即使所有窗口都被隐藏，主进程仍然运行，并继续维护计时状态。

#### 3.3.2 Renderer 渲染进程

渲染进程负责页面展示，包括：

1. 计时设置页面
2. 菜单页面
3. 计时显示页面
4. 计时详情页面
5. 计时完成页面
6. 计时开始提示
7. 专注完成提示

渲染进程不直接操作文件系统，也不直接维护核心计时逻辑。页面需要获取计时状态或发起控制操作时，通过 preload 暴露的 API 调用主进程。

#### 3.3.3 Preload 预加载脚本

Preload 负责在主进程和渲染进程之间建立安全边界。渲染进程不能直接访问 Node.js API，而是通过 preload 暴露有限的 `window.tomatoApi` 接口。

Electron 官方也推荐通过 preload 脚本安全地向渲染进程暴露特权 API。`contextBridge` 可以在隔离上下文之间建立安全桥接。

示例接口：

```ts
window.tomatoApi.startTimer(settings);
window.tomatoApi.pauseTimer();
window.tomatoApi.resumeTimer();
window.tomatoApi.restartTimer();
window.tomatoApi.getTimerState();
window.tomatoApi.showMenuWindow();
window.tomatoApi.showTimerDisplayWindow();
window.tomatoApi.updateSettings(settings);
```

## 4. 进程设计

### 4.1 窗口类型

本项目建议将页面映射为多个窗口，而不是所有页面都放在同一个窗口中。原因是 tomato 具有明显的桌面小工具特征，不同页面的显示位置、大小和行为不同。

| 窗口           | 类型           | 显示位置           | 说明                           |
| -------------- | -------------- | ------------------ | ------------------------------ |
| 设置窗口       | 普通窗口       | 屏幕中央           | 初次打开或再次专注时显示       |
| 菜单窗口       | 小型控制窗口   | 屏幕中央或托盘附近 | 用于暂停、恢复、重启、显示计时 |
| 计时显示窗口   | 小型悬浮窗口   | 屏幕右下角         | 显示当前状态和剩余时间         |
| 计时详情窗口   | 普通小窗口     | 屏幕中央           | 显示进度条、状态、设置         |
| 完成窗口       | 普通小窗口     | 屏幕中央           | 本轮计时完成后显示             |
| Toast 提示窗口 | 无边框提示窗口 | 屏幕右下角         | 显示计时开始、专注完成提示     |

### 4.2 窗口管理原则

所有窗口都由 `WindowService` 统一管理。页面组件不应该自行创建或销毁窗口。

`WindowService` 的职责包括：

1. 创建窗口
2. 显示窗口
3. 隐藏窗口
4. 关闭窗口
5. 控制窗口位置
6. 控制窗口置顶
7. 控制窗口是否显示在任务栏
8. 向窗口发送计时状态更新

示例：

```ts
class WindowService {
  showSettingsWindow(): void {}
  hideSettingsWindow(): void {}

  showMenuWindow(): void {}
  hideMenuWindow(): void {}

  showTimerDisplayWindow(): void {}
  hideTimerDisplayWindow(): void {}

  showTimerDetailWindow(): void {}
  showCompleteWindow(): void {}

  showStartToast(): void {}
  showFocusCompleteToast(): void {}
}
```

### 4.3 启动后的窗口行为

tomato 启动后的基本流程如下：

```text
用户打开 tomato.exe
        ↓
读取本地计时设置
        ↓
显示计时设置页面
        ↓
用户点击开始计时
        ↓
保存本轮设置
        ↓
启动计时状态机
        ↓
隐藏设置页面
        ↓
显示计时开始提示
        ↓
如果勾选显示计时，则显示计时显示窗口
        ↓
否则仅后台运行
```

需求文档中也说明，用户点击启动计时后，右下角会弹出计时开始提示，随后 tomato 关闭页面并进入后台运行；如果用户勾选了显示计时，则右下角弹出计时显示页面。

## 5. 计时状态维护设计

### 5.1 计时状态维护位置

核心计时状态应该维护在 Electron 主进程中的 `TimerService`，而不是维护在 React 页面组件中。

原因如下：

1. tomato 计时开始后默认隐藏窗口。
2. 计时显示窗口可能被关闭，但计时仍然需要继续。
3. 菜单窗口和详情窗口可能随时打开，需要读取同一份计时状态。
4. 如果计时状态放在某个页面组件中，窗口关闭或重新加载后状态容易丢失。
5. 主进程生命周期更适合作为后台计时控制中心。

因此，React 页面只负责显示状态和发送控制命令，真实计时状态由 `TimerService` 维护。

### 5.2 不建议只使用 remainingSeconds

不建议将计时逻辑设计为简单的：

```ts
remainingSeconds--;
```

这种方式存在问题：

1. 应用后台运行时定时器可能不稳定。
2. 系统休眠、卡顿或窗口隐藏时可能造成时间偏差。
3. 暂停、恢复、重启等逻辑难以维护。
4. 多窗口同时显示时，状态同步容易混乱。

更推荐使用基于时间戳的计时模型。

### 5.3 推荐的计时状态模型

计时状态可以定义为：

```ts
type TimerPhase = 'idle' | 'focus' | 'break' | 'completed';

type TimerStatus = 'idle' | 'running' | 'paused' | 'completed';

interface TimerSettings {
  focusMinutes: number;
  breakMinutes: number;
  showTimer: boolean;
}

interface TimerState {
  phase: TimerPhase;
  status: TimerStatus;

  focusMinutes: number;
  breakMinutes: number;

  startedAt: number | null;
  phaseStartedAt: number | null;
  expectedPhaseEndAt: number | null;

  pausedAt: number | null;
  totalPausedMs: number;

  lastRemainingSeconds: number;
}
```

字段说明：

| 字段                 | 含义                                       |
| -------------------- | ------------------------------------------ |
| phase                | 当前阶段，可能是未开始、专注、休息、已完成 |
| status               | 当前状态，可能是运行中、暂停中、已完成     |
| focusMinutes         | 本轮专注时长                               |
| breakMinutes         | 本轮休息时长                               |
| startedAt            | 本轮计时开始时间                           |
| phaseStartedAt       | 当前阶段开始时间                           |
| expectedPhaseEndAt   | 当前阶段理论结束时间                       |
| pausedAt             | 暂停开始时间                               |
| totalPausedMs        | 当前阶段累计暂停时长                       |
| lastRemainingSeconds | 暂停时记录的剩余秒数                       |

### 5.4 剩余时间计算方式

运行中时，不直接依赖每秒递减，而是根据当前时间和结束时间计算：

```ts
function getRemainingSeconds(state: TimerState): number {
  if (!state.expectedPhaseEndAt) return 0;

  if (state.status === 'paused') {
    return state.lastRemainingSeconds;
  }

  const remainingMs = state.expectedPhaseEndAt - Date.now();
  return Math.max(0, Math.ceil(remainingMs / 1000));
}
```

这种方式的好处是：

1. 即使界面刷新变慢，也不会影响真实计时。
2. 即使窗口隐藏，重新显示时仍能计算正确剩余时间。
3. 只要 `expectedPhaseEndAt` 正确，倒计时就能恢复正确状态。

### 5.5 开始计时

用户点击“开始计时”后，`TimerService` 创建新的计时状态。

```ts
function startTimer(settings: TimerSettings): void {
  const now = Date.now();

  state = {
    phase: 'focus',
    status: 'running',

    focusMinutes: settings.focusMinutes,
    breakMinutes: settings.breakMinutes,

    startedAt: now,
    phaseStartedAt: now,
    expectedPhaseEndAt: now + settings.focusMinutes * 60 * 1000,

    pausedAt: null,
    totalPausedMs: 0,

    lastRemainingSeconds: settings.focusMinutes * 60,
  };
}
```

开始计时后，主进程应执行以下操作：

```text
1. 保存本轮设置
2. 启动 TimerService
3. 隐藏设置窗口
4. 显示计时开始提示
5. 根据 showTimer 判断是否显示计时显示窗口
6. 通知所有已打开窗口更新状态
```

### 5.6 暂停计时

暂停时，不修改阶段，只记录暂停时间和当前剩余时间。

```ts
function pauseTimer(): void {
  if (state.status !== 'running') return;

  state.lastRemainingSeconds = getRemainingSeconds(state);
  state.pausedAt = Date.now();
  state.status = 'paused';
}
```

菜单页面中，暂停后按钮应从“暂停计时”变为“恢复计时”。需求文档也明确要求该按钮存在状态变化。

### 5.7 恢复计时

恢复计时时，需要根据暂停时的剩余秒数重新计算结束时间。

```ts
function resumeTimer(): void {
  if (state.status !== 'paused') return;

  const now = Date.now();

  state.expectedPhaseEndAt = now + state.lastRemainingSeconds * 1000;
  state.pausedAt = null;
  state.status = 'running';
}
```

这样可以保证暂停了多久都不会影响剩余时间。

### 5.8 重启计时

重启计时表示恢复到本轮计时刚启动的状态，即重新从专注阶段开始计时。需求文档中也说明，用户点击“重启计时”后，tomato 应恢复到计时刚启动的状态，即重新从专注计时开始。

```ts
function restartTimer(): void {
  const now = Date.now();

  state.phase = 'focus';
  state.status = 'running';
  state.phaseStartedAt = now;
  state.expectedPhaseEndAt = now + state.focusMinutes * 60 * 1000;
  state.pausedAt = null;
  state.totalPausedMs = 0;
  state.lastRemainingSeconds = state.focusMinutes * 60;
}
```

### 5.9 专注阶段完成

当专注阶段剩余时间为 0 时，系统进入休息阶段。

```ts
function completeFocusPhase(): void {
  const now = Date.now();

  state.phase = 'break';
  state.status = 'running';
  state.phaseStartedAt = now;
  state.expectedPhaseEndAt = now + state.breakMinutes * 60 * 1000;
  state.pausedAt = null;
  state.totalPausedMs = 0;
  state.lastRemainingSeconds = state.breakMinutes * 60;
}
```

同时主进程应执行：

```text
1. 显示专注完成提示
2. 播放两次提示音
3. 切换到休息计时
4. 通知已打开窗口更新状态
```

需求文档中说明，专注计时完成时，右下角弹出“专注结束，该休息啦”，并伴随两次滴滴声提醒用户。

### 5.10 休息阶段完成

当休息阶段结束时，本轮计时完成。

```ts
function completeBreakPhase(): void {
  state.phase = 'completed';
  state.status = 'completed';
  state.expectedPhaseEndAt = null;
  state.lastRemainingSeconds = 0;
}
```

同时主进程应执行：

```text
1. 显示计时完成页面
2. 隐藏或保留计时显示窗口，根据产品设计决定
3. 等待用户选择“再次专注”或“结束”
```

需求文档中说明，本轮计时完成时会自动弹出计时完成页面。用户点击“再次专注”时跳转到计时设置页面，且默认填充上一次专注设置；用户点击“结束”时关闭 tomato 的所有页面，但不关闭 tomato 程序本身。

## 6. 状态同步机制

### 6.1 状态读取

渲染进程可以通过 API 主动读取当前计时状态：

```ts
const state = await window.tomatoApi.getTimerState();
```

适用场景：

1. 窗口首次打开
2. 详情页打开时
3. 菜单页打开时
4. 计时显示窗口重新显示时

### 6.2 状态推送

主进程应在状态变化时主动向所有相关窗口推送事件：

```ts
mainWindow.webContents.send('timer:state-changed', state);
```

状态变化包括：

```text
开始计时
暂停计时
恢复计时
重启计时
专注完成
休息完成
显示计时设置变化
```

### 6.3 页面刷新频率

不建议主进程每秒向渲染进程推送完整状态。更推荐：

1. 主进程维护真实状态。
2. 页面打开后每秒本地刷新显示。
3. 每次刷新时根据主进程返回的 `expectedPhaseEndAt` 计算剩余时间。
4. 关键状态变化由主进程主动推送。

例如计时显示窗口可以在本地每秒计算剩余时间：

```ts
const remainingSeconds = Math.max(
  0,
  Math.ceil((expectedPhaseEndAt - Date.now()) / 1000)
);
```

这样可以减少 IPC 通信，也能保持显示流畅。

## 10. 核心业务流程设计

### 10.1 简单计时流程

```text
打开 tomato.exe
    ↓
显示计时设置页面
    ↓
用户设置专注时间和休息时间
    ↓
点击开始计时
    ↓
保存设置
    ↓
启动专注计时
    ↓
隐藏设置页面
    ↓
显示计时开始提示
    ↓
根据 showTimer 决定是否显示计时显示窗口
    ↓
专注计时结束
    ↓
显示专注完成提示
    ↓
进入休息计时
    ↓
休息计时结束
    ↓
显示计时完成页面
    ↓
用户选择再次专注或结束
```

### 10.2 暂停和恢复流程

```text
用户通过热键或托盘打开菜单页面
    ↓
点击暂停计时
    ↓
TimerService 记录剩余时间
    ↓
状态变为 paused
    ↓
菜单按钮变为恢复计时
    ↓
用户点击恢复计时
    ↓
TimerService 根据剩余时间重新计算结束时间
    ↓
状态变为 running
```

### 10.3 重启计时流程

```text
用户打开菜单页面
    ↓
点击重启计时
    ↓
TimerService 重置为本轮专注阶段开始状态
    ↓
重新从 focusMinutes 开始倒计时
    ↓
更新所有已打开窗口
```

### 10.4 显示和隐藏计时窗口流程

```text
用户勾选显示计时
    ↓
WindowService 显示计时显示窗口
    ↓
用户取消显示计时
    ↓
WindowService 隐藏计时显示窗口
```

计时显示窗口的显示与否不影响计时状态。计时状态只由 `TimerService` 维护。

## 14. 总结

tomato 是一个轻量级桌面番茄钟应用，核心技术路线建议采用：

```text
Electron + React + TypeScript + Vite + Tailwind CSS
```

架构上，应将应用拆分为主进程、预加载脚本和渲染进程三部分。主进程负责计时状态、窗口管理、托盘、热键、通知和本地存储；渲染进程负责页面展示和用户交互；preload 负责安全暴露 API。

计时状态应由主进程中的 `TimerService` 统一维护，不应放在 React 页面组件中。计时方式应基于时间戳和理论结束时间计算，而不是简单地每秒递减剩余秒数。这样可以保证窗口隐藏、重新打开、暂停恢复和系统卡顿等场景下计时仍然准确。

第一版使用 JSON 文件保存计时设置即可。后续如果增加学习记录、统计和任务管理，可以再引入 SQLite。

通过这种架构，tomato 可以保持简单、低干扰、易维护，同时为后续扩展保留空间。
